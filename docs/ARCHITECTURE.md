# 家具 AI 设计系统：架构与数据约定

版本：0.1 · 决策日期：2026-10-15

本文说明当前第一阶段的实现方向和未来扩展边界。所列接口、实体和执行流程是设计约定；实际端点、字段名称及已支持取值以共享 schema 和代码为准。后续 CAD、Blender 工作节点与工厂知识模块仍属于规划。

## 1. 当前原型技术选择

| 层 | 当前选择 | 原因 |
| --- | --- | --- |
| 客户端 | React、JavaScript、Vite | 建立响应式外观工作台与版本交互 |
| 三维预览 | Three.js、React Three Fiber | 浏览器实时显示网格、材质和光照 |
| 服务端 | Node.js、JavaScript、Express | 与前端共享 schema 和验证，一套运行时启动原型 |
| 数据验证 | Zod 共享 schema | 限制模型输出、客户端数据与保存格式 |
| 模型接入 | 服务端 OpenAI-compatible 请求 | 通过配置替换模型提供方，密钥不进入浏览器 |
| 无配置体验 | 明确标示的本地规则演示 | 支持离线试用有限命令，避免假冒模型能力 |
| 项目存储 | 本地 JSON | 单机快速验证保存与版本恢复 |
| 导出 | PNG、GLB、JSON | 分别用于画面确认、三维查看与保留外观数据 |

此前方案中的 Python/FastAPI 是后续工程服务的候选。当前采用 Node/Express 以减少原型安装成本；未来 Blender、CAD、计算工具独立执行，不要求为它们重写客户工作台或立即迁移业务后端。

## 2. 运行结构

```text
React 工作台
 ├─ 三维场景、材质与视角
 ├─ 对话、局部锁定与历史
 └─ PNG / GLB / JSON 导出
          │ HTTP
Express API
 ├─ 项目读取与保存
 ├─ 语言修改请求与配置状态
 ├─ schema 校验与受约束修改
 └─ provider 适配器
      ├─ 已配置：OpenAI-compatible 模型服务
      └─ 未配置：本地规则演示
          │
本地项目 JSON
```

页面对确定性的操作，例如材质切换和视角切换，直接更新本地预览。自然语言请求通过服务端解释，得到受约束的场景修改，经过验证后形成新的快照。保存失败不应清除浏览器中的当前设计。

## 3. 场景表示

第一阶段使用可编辑部件场景，包含柜体、门面、柜脚、把手等支持的部件，以及材质、分区与总体比例。它服务于视觉编辑，不描述榫接、孔位、加工公差、载荷或完整制造结构。

外观场景应具有明确单位约定和 schema 版本。即使 UI 不提供工程参数表，内部仍需足够信息来稳定重建同一外观。界面中的大致尺寸不得自动视为测量或生产尺寸。

建议的逻辑实体如下；初期可以放在同一项目 JSON 中：

| 实体 | 职责 | 必要信息 |
| --- | --- | --- |
| Project | 一个客户设计项目 | 标识、名称、阶段、当前场景、创建与更新时间 |
| AppearanceScene | 当前可重建外观 | 格式版本、家具类别、形体、部件、材质 |
| EditRequest | 一次用户修改意图 | 输入文本、基准场景、锁定信息 |
| EditResult | 可验证的修改结果 | 修改建议、处理模式、实际变化说明、未支持项 |
| HistorySnapshot | 撤销/重做 | 有效场景、必要编辑状态、顺序 |
| SavedVersion | 用户主动保存的版本 | 标识、名称、完整场景快照、时间 |
| AppearancePackage | 可携带的外观数据 | 项目与格式版本、当前场景、视觉状态与工程状态声明 |

外部分享包不应默认包含密钥、服务配置、原始内部日志或工厂资料。对话全文是否随包导出应根据产品需要另行明确，不因为存在于内存就自动打包。

## 4. 语言修改的边界

模型承担意图解释，不直接控制浏览器、系统命令或文件路径。标准流程：

1. 接收用户文本、当前场景和锁定信息。
2. 选择模型服务或明确的本地演示解析器。
3. 生成有限字段的修改建议及简短说明。
4. 对类别、枚举、数值、长度和对象结构进行检查。
5. 合并修改时保留未涉及字段，并再次执行锁定约束。
6. 验证最终场景；只有有效场景才能成为新快照。
7. 返回实际应用结果，展示新外观或明确错误。

即使 prompt 已说明锁定规则，最终仍必须由代码执行。模型输出不得变成任意 Python、JavaScript 或 Shell 程序执行。

客户端应避免把旧请求结果覆盖到更新的设计。原型可以串行处理语言请求或在请求期间限制冲突修改；后续可使用场景版本号进行并发控制。

## 5. 状态和版本语义

- 当前场景是工作中的状态；撤销栈保存已应用的有效快照。
- 在撤销后执行新修改，应清除不再属于当前分支的重做记录。
- 保存版本应复制当前场景，不能只保存会随编辑变化的对象引用。
- 恢复保存版本应整体恢复其场景，避免将两份设计的字段意外混合。
- 单次对话、按钮编辑或材质切换应产生可理解的修改边界，避免拖动时产生过多历史项。
- 选中状态、工具面板开合和镜头操作通常不需要形成家具设计版本。
- 正式“客户确认”需要独立业务记录；首轮的“保存版本”不等同于审批。

## 6. 导出和视觉一致性

**PNG** 记录当前展示视图。后续确认包应统一正、侧、背等视图和光照，便于比较。

**GLB** 保存可展示的家具网格和材质。背景、灯光辅助物、地面和选中装饰不应无意变成家具零件。外部查看器可能具有不同的环境光与色调映射，交付时不应承诺逐像素一致。

**JSON** 保存可重新生成外观的结构化数据与格式版本。GLB 是展示交付物，不应替代可编辑源数据；没有参数来源的任意 GLB 也不能假定可无损变成项目场景。

所有导出物都属于外观阶段，不证明尺寸适合生产或结构可靠。

## 7. 持久化与失败处理

本地 JSON 适合单机原型。应把存储路径限制在指定数据目录，并验证项目标识，不接受用户提供的任意路径。

写入尽量采用先写临时文件再替换的方式，减少进程中断造成损坏。损坏、缺失或格式不兼容的文件应报告明确错误，不能静默覆盖旧项目。

生产部署前需要补齐用户认证、项目权限、数据库事务、并发编辑控制、备份恢复和审计。这些功能不因为原型在本机可运行而自动视为具备。

## 8. 配置与依赖边界

前端只需浏览器支持 WebGL。开发环境需要兼容项目依赖的 Node.js 与包管理器。第一阶段的实时场景不要求安装 Blender、CUDA、CAD 或本地大语言模型。

模型提供方配置由服务端管理，包括服务地址、模型名称和密钥；具体变量名以 `.env.example` 为准。自定义服务地址需由部署者设置，不能允许普通客户随意修改为任意内部网络地址。

不把外部模型服务响应直接当成可信业务数据。不向前端返回密钥和完整敏感错误堆栈；可用错误码与简要说明支持排查。

## 9. 验证策略

优先检查高风险逻辑：模型结果校验、锁定保持、未修改字段保持、无配置模式、版本快照和存储恢复。不要只测试与实现完全相同的重复计算。

对三维场景必须执行浏览器检查，包括：页面可用、模型完整、材质变化、不同视角、局部编辑、撤销/重做、错误反馈和导出。构建与类型检查用于发现集成问题，不能替代视觉验收。

外部模型未配置时，应如实报告仅验证本地演示流程；未实际调用的供应商不能列入已验证范围。第一阶段不运行工程承载测试，也不产生工程可靠性结论。

## 10. 后续扩展结构

```text
项目与版本业务服务
 ├─ 外观服务：场景资产 / 语言编辑 / 渲染
 ├─ 设计深化服务：CAD 重建 / 尺寸 / 视图对照
 └─ 工程服务：装配 / 工艺 / 计算 / 图纸 / 审批
            │ 任务队列与文件协议
执行节点：Blender / CAD / 仿真或计算 / 图纸解析
            │
数据库 + 对象存储 + 检索索引 + 可执行工厂规则
```

执行节点应有任务目录、超时、资源限制、日志和结果清单。耗时渲染与 CAD 操作不能阻塞客户 API 进程。执行失败要保留输入与诊断信息，并允许重试。

后续分别维护展示模型、精确设计模型和生产装配模型，通过项目、部件映射和版本关联。应记录它们之间的差异，不能只保存“最新模型”而丢失客户确认依据。

## 11. 后续工程证据模型

生产工程阶段需扩展以下信息：

| 记录 | 关键内容 |
| --- | --- |
| Requirement | 客户要求、实测数据、来源及确认状态 |
| FactoryCapability | 工厂、设备、材料、能力边界及有效版本 |
| DesignRule | 规则表达式、依据、适用条件与审批人 |
| EngineeringCheck | 输入版本、检查工具、阈值、结果与失败说明 |
| Calculation | 材料性能、载荷、边界条件、方法与结论 |
| TrialResult | 样件、试验条件、结果、返修和安装反馈 |
| Approval | 审核人、受控版本、意见与发布时间 |
| ChangeImpact | 变更原因、受影响图纸/物料/计算、重新验证状态 |

AI 检索到的经验是候选依据。只有适用条件一致且经过验证的规则，才可以作为工程约束执行。生产状态应由明确审核和证据驱动，不能由模型自由生成。
